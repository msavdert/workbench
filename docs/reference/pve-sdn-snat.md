# PVE host: guest SNAT missing after boot (SDN post-up race)

The Proxmox host `pve` is deliberately **not** managed by this repository
(see `pve-nic-hang.md` for the same rule). The change below was applied by
hand on 2026-10-16 and is recorded here rather than encoded. This file is
the procedure for re-applying it after a host reinstall and for backing it
out.

## The failure

After a `pve` reboot the box reached its gateway (10.0.0.1, `vnet0` on the
host) but nothing beyond it: no ping to 1.1.1.1, DNS timing out. `pve` itself
was online and `net.ipv4.ip_forward` was 1. The `nat` table held only
Tailscale's `ts-postrouting` jump; the SNAT rule for `10.0.0.0/24` was absent.

The rule is declared by Proxmox SDN (zone `localnat`, subnet with `snat 1`)
as a `post-up` hook in the generated `/etc/network/interfaces.d/sdn`.
ifupdown2 runs that hook without `-w`, so iptables exits at once when another
process holds the xtables lock. The host journal of that boot
(`journalctl -b -u networking`):

```
warning: vnet0: post-up cmd 'iptables -t nat -A POSTROUTING -s '10.0.0.0/24' -o vmbr0 -j SNAT --to-source 88.99.150.113' failed: returned 4 (Can't lock /run/xtables.lock: Resource temporarily unavailable
```

The `raw` rule from the same stanza (`-i fwbr+ -j CT --zone 1`) failed the
same way.

## Why it showed up now

The race is old: in the 2026-10-04 boot `tailscaled` also started in the same
second as the `networking` post-up hooks, and none of the three earlier boots
logged a lock failure. The 2026-10-16 upgrade (kernel 7.0.14-24, tailscale
1.102.4 to 1.104.1) became active only with this reboot. That it shifted the
timing is an inference, not confirmed; the lock holder was not logged, and
`tailscaled` setting up its own `ts-*` chains is the likely one. Either way
the root cause is the hook running without `-w`, so it can recur on any boot.
It did on the very next one: the verification reboot at 02:30 UTC on
2026-10-17 lost the race again, that time on the `raw` rule only, and the
unit below re-added it two seconds later.

## What was changed on the host

`/etc/network/interfaces.d/sdn` is regenerated by every SDN apply, so it is
not edited. Instead a oneshot unit replays its rules after boot:

- `/usr/local/sbin/sdn-iptables-ensure.sh` reads every `post-up iptables` /
  `ip6tables` line from the SDN file that appends or inserts a rule (`-A`,
  `-I`), checks it with `-C`, and adds only the missing ones, with `-w 30`.
  Other commands (`-N`, `-F`, `-P`, ...) are skipped, since a `-C` check of
  them would run them for real. A `-C` that fails for any reason, a syntax
  error included, counts as "missing"; the parsing above keeps that to the
  real case for every form SDN emits. The SDN file stays the single source of the
  rules; a re-run is a no-op. Each rule it adds is logged under the tag
  `sdn-iptables-ensure`.
- `/etc/systemd/system/sdn-iptables-ensure.service`, ordered after
  `networking`, `tailscaled` and `pve-firewall` and before `pve-guests`,
  enabled in `multi-user.target`.

It runs once per boot. A lock failure during a later SDN apply or
`ifreload` is not repaired on its own; `systemctl restart
sdn-iptables-ensure` replays the rules then.

The `post-down` hooks still match the replayed rules exactly, so `ifdown`
and SDN applies remove them as before.

## Checking

```
ssh pve-vm-ssh 'iptables -t nat -S POSTROUTING; journalctl -b -t sdn-iptables-ensure --no-pager'
```

A line `added missing rule` in the current boot means the race happened and
the unit repaired it; no line means the hooks succeeded on their own.

## Re-applying after a host reinstall

Copy the two files below into place, then:

```
ssh pve-vm-ssh 'chmod 755 /usr/local/sbin/sdn-iptables-ensure.sh && systemctl daemon-reload && systemctl enable --now sdn-iptables-ensure.service'
```

## Rolling back

```
ssh pve-vm-ssh 'systemctl disable --now sdn-iptables-ensure.service && rm /etc/systemd/system/sdn-iptables-ensure.service /usr/local/sbin/sdn-iptables-ensure.sh && systemctl daemon-reload'
```

The rules already in place stay until the next reboot or SDN apply.

## `sdn-iptables-ensure.sh`

```bash
#!/usr/bin/env bash
# Re-adds the iptables rules declared as post-up hooks in the Proxmox SDN
# config when they are missing. ifupdown2 runs those hooks without -w, so at
# boot they fail outright if another process holds the xtables lock; on
# 2026-10-16 that left vnet0 (10.0.0.0/24) with no SNAT and the guests offline.
# The SDN file stays the single source of the rules; this only replays them.
set -euo pipefail

sdn=/etc/network/interfaces.d/sdn
[[ -r $sdn ]] || exit 0

# Only append/insert rules can be tested with -C; any other command (-N, -F,
# -P, ...) would run for real in the check, so it is left to ifupdown2.
add_re=' -[AI] '

status=0
while IFS= read -r cmd || [[ -n $cmd ]]; do
  # One space between words, so the patterns below can rely on it.
  cmd=$(sed -E 's/[[:space:]]+/ /g; s/ $//' <<<"$cmd")
  [[ " $cmd " =~ $add_re ]] || continue
  bin=${cmd%% *}
  args=${cmd#* }
  # -C takes no rule number, so drop the one an -I may carry.
  check=$(sed -E 's/(^| )-[AI] ([^ ]+)( [0-9]+)? /\1-C \2 /' <<<"$args ")
  if eval "$bin -w 30 $check" 2>/dev/null; then
    continue
  fi
  if eval "$bin -w 30 $args"; then
    logger -t sdn-iptables-ensure "added missing rule: $cmd"
  else
    logger -t sdn-iptables-ensure "failed to add rule: $cmd"
    status=1
  fi
done < <(sed -nE 's/^[[:space:]]*post-up[[:space:]]+(((\/usr)?\/sbin\/)?ip6?tables[[:space:]].*)$/\1/p' "$sdn")
exit "$status"
```

## `sdn-iptables-ensure.service`

```ini
[Unit]
Description=Replay missing Proxmox SDN iptables rules (vnet0 SNAT)
After=networking.service tailscaled.service pve-firewall.service
Before=pve-guests.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/sdn-iptables-ensure.sh
RemainAfterExit=yes
# Each rule may wait up to 30 s twice on the xtables lock.
TimeoutStartSec=5min

[Install]
WantedBy=multi-user.target
```
